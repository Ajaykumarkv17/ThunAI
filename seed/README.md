# `seed/seed_dataset.json` — synthetic responders, shelters, and aggregate resident points

This file holds the responder, shelter, and aggregate resident-point rows
that `scripts/seed.sh` (task 11.5, not yet implemented) writes into the
**real** `thunai-state` DynamoDB table. Unlike `seed/hazard_readings/`, this
is not a synthetic *backend* — the data here is synthetic content written
into a live store, per design.md §3.9: "The seed data is synthetic content
written into real stores, not a synthetic backend."

Generated by the committed, deterministic generator:

```bash
python seed/_generate_seed_dataset.py
```

Re-running it with the fixed seed reproduces byte-identical output. The
generator is not imported by application code — `scripts/seed.sh` reads the
committed `seed_dataset.json` directly.

## Top-level structure

```json
{
  "responders": [ ... 14 objects ... ],
  "shelters": [ ... 3 objects ... ],
  "resident_points": [ ... 900 objects ... ]
}
```

### `responders` (14 rows)

Each object is constructed via `Responder(...).model_dump()` from
`schemas/entities.py`, so it deserialises into `schemas.entities.Responder`
with **zero transformation**:

| Field | Notes |
|---|---|
| `responder_id` | `resp-01` .. `resp-14` |
| `name` | synthetic first name + last-initial only (e.g. `"Karthik R."`) — no real people (Req 18.1) |
| `home_coords` | `[lat, lon]` tuple in the Kollidam Ward-7 river-reach region (11.20-11.30 lat / 79.80-79.90 lon), the same region already used by `tests/unit/test_entities_schema.py` and `tests/unit/test_state_store.py` fixtures |
| `equipment` | cycles through `["boat"]`, `["4x4"]`, `["boat", "4x4"]`, `["none"]` so all four combinations are represented |
| `availability_status` | `"AVAILABLE"` for every row — a fresh seed starts every responder available |
| `active_assignment_id` | `null` for every row |
| `active_assignment_count` | `0` for every row |

### `shelters` (3 rows)

Each object is constructed via `Shelter(...).model_dump()`, so it
deserialises into `schemas.entities.Shelter` with zero transformation.

| Field | Notes |
|---|---|
| `shelter_id` | `shelter-1` .. `shelter-3` |
| `name` | synthetic shelter names (`Ward-7 Community Hall`, `Riverside Colony School`, `Kanal Street Marriage Hall`) |
| `coords` | `[lat, lon]` in the same region as the responders |
| `total_capacity` | **50 / 40 / 30**, summing to **120** — an uneven-but-plausible split (one large community hall, one mid-size school, one smaller hall), matching design.md §3.9's own worked example ("total capacity summing to 120 (e.g. 50/40/30)") |
| `available_capacity` | equal to `total_capacity` for every row — a fresh seed starts every shelter empty, per design.md §3.9 ("current placements = 0 at seed") |

### `resident_points` (900 rows)

Design.md §3.9 describes these as "~900 synthetic resident location points
along the reach (used only for aggregate affected-area counts, Req 14.5 —
never individually exposed)." This is explicitly aggregate/statistical data
per Req 18.1/18.2's data-minimisation requirement — no names, no individual
identifiers, no household-level location detail, only an area label, a
coordinate, and an occupant count per point:

| Field | Notes |
|---|---|
| `point_id` | `rp-0001` .. `rp-0900` |
| `area_id` | one of five ward-area labels (`Ward-7 North`, `Ward-7 South`, `Riverside Colony`, `Kanal Street`, `Old Ferry Road`), matching the area-name style already used in design.md's own escalation-template examples |
| `coords` | `[lat, lon]` in the same region as the responders/shelters |
| `occupant_count` | a positive integer, weighted so most points represent a single-occupant household, a meaningful minority represent 2-3 occupants, and a few represent 4-6 — a plausible household-size mix for a river-ward setting |

**Population-total reasoning.** Design.md's Overview states the ward has
"~900 residents on a monitored river reach." Rather than treating "~900
resident points" as literally 900 individual residents (which would
contradict the aggregate-only framing of Req 14.5/18.1), this dataset
generates 900 points as *aggregate household/cluster markers*, each carrying
an `occupant_count`. The resulting aggregate occupant total (~2,300, printed
by the generator on each run) is a plausible total population for a ward
whose committee-facing framing quotes "~900 residents" as a rounded,
order-of-magnitude figure rather than an exact census count — consistent
with design.md's own hedge ("~900"). If a future task needs the aggregate
total to land closer to exactly ~900, the `OCCUPANT_COUNT_CHOICES` weighting
in `seed/_generate_seed_dataset.py` is the single place to adjust; the point
*count* (900) and the *shape* of each row are not affected by that choice.

## Validation

`tests/unit/test_seed_dataset.py` loads this file and asserts every row
constructs successfully as its corresponding `schemas.entities` model (not
just visual conformance), plus the fresh-seed invariants above.
